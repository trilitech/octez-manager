# Release plan: v1.0.0-rc4 — 2026-07-31

## Context

- Latest tag: `v1.0.0-rc3` (2026-05-26, commit `3509eac1` lineage).
- `main` is clean and in sync with `origin/main` at `739d49d4`.
- 22 commits landed since rc3 — all bug fixes, tests, and CI changes (no new features).
  Highlights: IPv6 host:port validation (#1006), enable-on-boot persistence (#1001),
  archive-node snapshot conflict (#1000), baker/accuser global-args preservation (#996),
  env-file quote accumulation (#995), `instance remove --yes` (#998), Esc discard
  confirmation (#975), instance-name validation (#966), pre-install binary access
  validation (#987), integration tests bumped to Octez v25.
- The CHANGELOG `[Unreleased]` section already documents all user-facing changes.

## Scope decision

Release is cut from current `main` (`739d49d4`). None of the 10 open PRs are included —
they remain open and will land in a later release. If any open PR must ship in rc4, it
must be merged to `main` **before** the version-bump PR is created.

## Steps

1. **Branch**: create `release/v1.0.0-rc4` from `main` (no direct pushes to main).
2. **Version bump**:
   - `dune-project` line 3 → `(version 1.0.0-rc4)`
   - `octez-manager.opam` line 3 → `version: "1.0.0-rc4"`
   - No other files hardcode the release version (the CLI derives its version from
     build info since `04106f53`; rc strings in `test_self_update_checker*.ml` are
     comparison fixtures, not the app version).
3. **CHANGELOG**: insert `## [1.0.0-rc4] - 2026-07-31` under `## [Unreleased]`,
   moving all current Unreleased entries into the new section; leave `[Unreleased]`
   empty.
4. **Verify locally**: `dune build`, `dune runtest`, `dune fmt`,
   `./scripts/check-copyright.sh`.
5. **Commit & PR**: single commit `chore: prepare v1.0.0-rc4 release`; open a PR
   against `main`. No changelog entry needed beyond the section cut itself.
6. **User merges the PR** (no auto-merge; merge is the user's call after review).
7. **Tag after merge**: once the release-prep commit is on `main`, tag **that**
   commit `v1.0.0-rc4` and push the tag. Pushing the tag triggers the CI `release`
   job: `dune build --release`, checksum generation, and GitHub release creation
   with the `octez-manager-v1.0.0-rc4-linux-x86_64` binary.

## Ordering constraint (important)

The tag must point at a commit that already contains the version bump. Tagging
current `main` before the PR merges would produce a GitHub release whose binary
reports `1.0.0-rc3` and whose changelog section doesn't exist.

## Decisions (2026-07-31)

- **Scope**: current `main` only; none of the open PRs are pulled in.
- **Tag timing**: user chose to tag immediately rather than after PR merge.
  To keep the released binary's self-reported version correct (it is stamped
  from `dune-project` via dune-build-info), the tag is pushed on the
  release-prep commit itself — which contains the version bump — rather than
  on `739d49d4`. CI starts the release build right away; the PR review happens
  in parallel. If review changes the release-prep commit, the tag must be
  moved (delete + re-push) before announcing the release.

## Rollback

- Before tag push: everything is a normal PR — close/revert as usual.
- After tag push: the GitHub release and tag would need manual deletion
  (`gh release delete`, `git push --delete origin v1.0.0-rc4`) — avoid by
  double-checking the tagged commit before pushing.
